# Feature Specification: Roles & Users

**Feature Branch**: `011-roles-and-users`
**Created**: 2026-09-29
**Status**: Draft
**Input**: User description: "Feature Brief — 011 Roles & Users. Two roles with per-section permissions, user management for the main admin, and permission checks applied across every admin feature built so far." (full brief recorded in `history/prompts/011-roles-and-users/`; carried-over acceptance items in `docs/briefs/011-roles-and-users.md`)

**References**: `docs/prd.md` §2, §6.1, §6.2 · Constitution III (Roles & Access), IV (Security), VI (Data Integrity), XI (three access cases per admin route) · Feature 002 (login, sessions, lockout) · Feature 010 (Account page, password change, sign out other devices)

## Overview

Today every signed-in admin can do everything. This feature introduces two roles:

- **Main admin** — full access, including user management and student registrations. The first main admin is created by the manually run setup (seed) command.
- **Content manager** — access only to the admin sections the main admin has granted.

Grantable sections, one permission key each: **news**, **messages**, **careers**, **settings**, **pages**. **Registrations** and **users** are main-admin only and can never be granted. Adding a future section means adding one key; the way permissions are granted, stored and checked does not change.

The main admin gets a Users area to create, edit, disable, re-enable, reset and delete accounts, and a record of every account and permission change. Every admin page, route and action built so far gains a server-side permission check.

## Clarifications

### Session 2026-09-29

- Q: Can there be more than one main admin? → A: Yes. The main admin can create another main admin and promote or demote other users; at least one active main admin must always remain.
- Q: Which permission governs the existing Signups list (004)? → A: The `careers` key governs Signups now, and Careers once 012 replaces it; no separate `signups` key.
- Q: Creating an account with a deleted user's email? → A: Restore that record as a brand-new account (the password just set, only the newly ticked grants, the newly chosen role, old sessions and password gone); its earlier change-record history is kept.
- Q: What does a signed-in user get from a request they may not make? → A: A uniform "forbidden" outcome (403) with no data, for every missing permission or wrong role, including main-admin-only areas; "not signed in" (401) is unchanged.

### Session 2026-09-29 (brief revised before implementation)

- Q: How is a user added or edited, and where does their password come from? → A: In a panel that slides in from the right over the Users list (not a separate page). It holds the email, the role, the password and — for a content manager only — the section tickboxes. The admin types the password or generates one with a click, and can reveal it to read it out; it is shown only while the panel is open. The main admin controls every password (see Session 2026-09-30). This replaces the earlier "password generated by the system and shown once with a copy button".
- Q: How does the main admin reset a password? → A: From the same panel on an existing user: filling the password field (typed or generated) resets it, ends the user's sessions and restarts the 7-day expiry. There is no separate reset control.
- Q: Which password field style is used across the admin? → A: One reusable password input with a show/hide eye toggle is used for every password field: login, the Account page's three fields (main admin only) and the user panel. It is hidden by default and goes back to hidden when its form is submitted or the panel closes.

### Session 2026-09-30 (owner decision: the main admin controls every password)

- Q: Can a content manager change their own password? → A: No. The main admin controls every password: a content manager's password is set by the main admin (typed or generated in the user panel) and only the main admin can change it. There is no forced change at first login, no temporary state and no 7-day expiry; the earlier "Set your password" first-login page is removed. A main admin still changes their own password on the Account page. This amends Constitution III (version 2.0.0). Trade-off accepted: the main admin knows each content manager's working password until they reset it.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Main admin creates a content manager (Priority: P1)

The main admin opens the Users page, which lists the existing users with an "Add user" button. Adding opens a panel that slides in from the right over the list. The panel holds the email, the role (main admin or content manager), the password, and — for a content manager only — the section tickboxes (a main admin implicitly has everything). The password can be typed or generated with one click, and revealed to read it out. Saving closes the panel and the new user is in the list immediately. The password the admin sets is the user's password. Only a main admin can change it later.

**Why this priority**: Without a way to create a second account, roles and permissions have no one to apply to. This is the entry point for every other story.

**Independent Test**: Signed in as main admin, add a content manager with "news" ticked using a generated password; confirm the panel slides in from the right, closes on save, the user is in the list as "Active" without a reload, and the password is not shown anywhere afterwards.

**Acceptance Scenarios**:

1. **Given** the main admin is on the Users page, **When** they choose "Add user", **Then** a panel slides in from the right over the list with the email, role, password and section tickboxes; **When** they enter a new email, tick "news" and "messages", set a password and save, **Then** the panel closes and the new user appears in the list immediately.
2. **Given** the panel is open with Content manager chosen, **When** the main admin chooses Main admin, **Then** the section tickboxes disappear (a main admin has everything); choosing Content manager again brings them back.
3. **Given** the password field, **When** it is first shown, **Then** its characters are hidden; an eye control reveals them so the admin can read them out, and hides them again. One click on "Generate" fills the field with a strong password and reveals it.
4. **Given** a typed password shorter than 12 characters or longer than 128, **When** the admin saves, **Then** a specific message is shown, the panel stays open and nothing is created.
5. **Given** the panel is open with anything typed or changed, **When** the admin presses Escape, clicks outside the panel, uses the close button or Cancel, **Then** they are warned first and can stay; with nothing typed it closes at once.
6. **Given** the panel was closed (saved or cancelled) or the page reloaded, **When** the main admin opens it again or views the user, **Then** no password is shown anywhere.
7. **Given** a phone-width screen, **When** the panel opens, **Then** it fills the full width.
8. **Given** an existing user `ayesha@school.pk`, **When** the main admin tries to add `Ayesha@School.PK`, **Then** it is refused with "An account with this email already exists" under the email field and nothing changes.
9. **Given** an invalid email, **When** the main admin saves, **Then** a field error is shown and no account is created.
10. **Given** a content manager is signed in, **When** they open the Users page URL or call any user-management request directly, **Then** the page redirects to the overview with the "no access" message and the request is refused without revealing data.

---

### User Story 2 - The main admin controls every password (Priority: P1)

A content manager logs in with the password the main admin gave them, and it works as it stands. They cannot change any password, their own included: the Account page shows no change-password form for them, and the server refuses the request even if it is sent directly. Only the main admin sets or changes a content manager's password, from that user's edit panel. A main admin changes their own password on the Account page, as in feature 010.

**Why this priority**: The owner wants a single point of control over credentials. It also means a stolen content-manager session can never be used to lock the real person out or plant a password only the attacker knows.

**Independent Test**: Add a content manager; log in as them; confirm they land on the overview with only their sections, the Account page shows a note instead of a password form, and a direct change-password request is refused. As main admin, set a new password for them in the edit panel and confirm the old one stops working and their sessions end.

**Acceptance Scenarios**:

1. **Given** an account whose password the main admin set, **When** the person logs in with it, **Then** they go straight to the overview: there is no forced password change and no temporary state.
2. **Given** a signed-in content manager, **When** they open the Account page, **Then** it shows their email, "Sign out other devices" and a note that their password is managed by the main admin, and no change-password form.
3. **Given** a content manager, **When** a change-password request is sent directly (including one naming another user's id or email), **Then** it is refused as forbidden and no password changes.
4. **Given** the main admin editing a user, **When** they fill the password field (typed or generated) and save, **Then** the old password stops working, the new one works as set, and that user's sessions end.
5. **Given** a main admin on their own Account page, **When** they enter the correct current password and a valid new one, **Then** their password changes under the 010 rules; they cannot change anyone else's password there.
6. **Given** any signed-in role, **When** they use "Sign out other devices", **Then** only their own other sessions end.

---

### User Story 3 - Permissions are enforced everywhere (Priority: P1)

Every admin page, request and action checks, on the server, whether the signed-in user may use that section. The sidebar, overview cards and notification bell show only what the user may use. A content manager who opens a forbidden page is sent to the overview with a clear message; a forbidden request is refused. Permission changes apply on the user's very next request, with no need to log out.

**Why this priority**: Constitution III: hiding a menu is presentation only. Without server checks, roles are cosmetic.

**Independent Test**: As a content manager with only "news", confirm the sidebar shows only Overview, News and Account; open `/admin/messages` and `/admin/signups` by URL and confirm the redirect and message; call the messages and signups requests directly and confirm refusal.

**Acceptance Scenarios**:

1. **Given** a content manager with only "news", **When** they view any admin page, **Then** the sidebar lists Overview, News and Account only; the overview shows only news-related cards; the notification bell shows no message or career-application counts.
2. **Given** that content manager, **When** they open the Messages page by URL, **Then** they are redirected to the overview and see "You don't have access to that section."
3. **Given** that content manager, **When** they send a messages request directly (list, read, change status, delete), **Then** it is refused and no message data is returned.
4. **Given** any content manager, whatever their grants, **When** they try to reach student registrations, user management, or the change record, by page or by request, **Then** they are refused.
5. **Given** a content manager is signed in on two browsers, **When** the main admin removes "news" from them, **Then** the next page load or request in either browser treats them as having no "news" access, without logging out.
6. **Given** a content manager, **When** they send a request that tries to change their own permissions or role (by any route, including a crafted field on an account action), **Then** it is refused or ignored and their permissions are unchanged.
7. **Given** a content manager with no grants, **When** they sign in, **Then** they see only the overview (with a short note that no sections have been granted yet) and their own Account page.

---

### User Story 4 - Managing users (Priority: P2)

The main admin sees every account with its email, role, permissions, status and last login. They can edit a user's permissions or role, disable and re-enable an account, reset its password, and delete it. Safeguards stop the main admin from locking themselves out and ensure at least one main admin always remains.

**Why this priority**: Needed to run the panel over time, but the first content manager can be created and used without it.

**Independent Test**: As main admin, edit a content manager's role and grants in the panel, disable them (their open session loses access on the next request), re-enable them, reset their password from the panel (sessions ended), then delete them; confirm each step in the list and the change record.

**Acceptance Scenarios**:

1. **Given** several accounts, **When** the main admin opens Users, **Then** each row shows email, role, granted sections (or "All" for a main admin), status (Active or Disabled) and last login ("Never" if none).
2. **Given** a content manager, **When** the main admin changes their ticked sections and saves, **Then** the new grants apply on that user's next request.
3. **Given** an active content manager with an open session, **When** the main admin disables them, **Then** all their sessions end immediately, their next request is refused, and they cannot log in ("This account is disabled" is not revealed at login; login shows the same generic failure as 002).
4. **Given** a disabled user, **When** the main admin re-enables them, **Then** they can log in again with their existing password and grants.
5. **Given** any other user, **When** the main admin fills the password field in that user's edit panel (typed or generated) and saves, **Then** the old password stops working, the new one works as set and all the user's sessions end; with the field left empty their password is untouched.
6. **Given** a user, **When** the main admin deletes them and confirms, **Then** the user disappears from the list, all their sessions end, they cannot log in, and their past entries in the change record remain.
7. **Given** the main admin viewing their own row, **When** they try to disable, delete or demote themselves, or edit their own role, **Then** those actions are not offered, and a direct request to do so is refused.
8. **Given** only one active main admin exists, **When** any action would leave zero active main admins (disable, delete or demote), **Then** it is refused with "At least one main admin must remain."
9. **Given** the main admin, **When** they change a content manager's role to main admin (or a second main admin to content manager), **Then** the change applies on that user's next request and is recorded.

---

### User Story 5 - Record of changes (Priority: P2)

Every account and permission change is recorded: who did it, to whom, what changed, and when. The main admin can view the list, newest first.

**Why this priority**: Constitution III requires it, and it answers "who gave this person access?" It does not block day-to-day use.

**Independent Test**: Perform a create, a grant change, a disable and a reset; open the change record and confirm four entries, newest first, each with actor, target, change and time, and no password anywhere.

**Acceptance Scenarios**:

1. **Given** the main admin changes a user's grants from {news} to {news, messages}, **When** they open the change record, **Then** the newest entry shows the main admin's email, the user's email, "Permissions: added messages", and the date and time.
2. **Given** a password reset or account creation, **When** its entry is viewed, **Then** it says a password was set, and the password itself appears nowhere.
3. **Given** more entries than fit on one screen, **When** the main admin scrolls or pages, **Then** older entries are reachable and order stays newest first.
4. **Given** a content manager, **When** they try to open the change record by page or request, **Then** they are refused.

---

### User Story 6 - Existing features gain checks (Priority: P2)

News, messages, signups/careers, settings, notification counts, and the 010 account actions all check permissions. The 010 account actions gain the "wrong role" test that 010 could not have.

**Why this priority**: Required by Constitution XI for every admin route. Much of it is delivered alongside User Story 3; this story makes the per-feature coverage explicit and complete.

**Independent Test**: Run the access test suite; every admin route shows three passing cases (no session, wrong role or missing permission, correct permission). Run the 010 carried-over cases from `docs/briefs/011-roles-and-users.md`.

**Acceptance Scenarios**:

1. **Given** each existing admin route, **When** called with no session, **Then** it is refused; **with** a session lacking the section's permission, **Then** it is refused; **with** the right permission, **Then** it succeeds.
2. **Given** the notification counts, **When** a content manager without "messages" asks for them, **Then** no message count is returned; registration counts are never returned to a content manager.
3. **Given** a content manager with no grants, **When** they open Account, **Then** they can change **their own** password and sign out **their own** other devices; the main admin's password and sessions are unaffected.
4. **Given** the main admin uses "Sign out other devices", **Then** the content manager's sessions stay signed in, and vice versa.
5. **Given** an account action request carrying a user id or email field, **When** it is processed, **Then** the field is ignored and only the caller's own account is affected.
6. **Given** a content manager reaches 5 wrong current-password attempts on Account, **Then** only their own password change is blocked; the main admin's is not.
7. **Given** any role, **When** the raw auth-library mutation routes closed in 010 are called, **Then** they still return "not found".

---

### Edge Cases

- A user disabled or deleted while signed in loses access on their next page load or request, in every browser.
- A user whose role or grants change mid-session gets the new access on their next request, in every browser; a page already open that then submits a now-forbidden action is refused.
- A content manager with no grants sees only the overview and their own Account page.
- A password set in the panel is never shown again after the panel closes, and never appears in logs, the change record, error messages, URLs or page source outside the open panel.
- Emails are compared in lowercase with surrounding spaces removed; the same email cannot belong to two accounts.
- Creating an account with the email of a **deleted** account restores that account as a new account (the password just set, the newly ticked grants and chosen role; nothing from before the deletion — grants, role, password, sessions — carries over), keeping its earlier change-record entries. It is recorded as a creation.
- Two main admins acting at once on the last two active main admins: at most one demote/disable/delete succeeds, so one main admin always remains.
- A password typed by the admin must meet the same minimum length as any other password; a shorter one is refused before anything is saved.
- The seed command's reset option still works as the recovery path for a main admin; it also makes the account a main admin again and clears any disabled or deleted state.
- Grants left over for a section the user's role doesn't need (e.g. a content manager promoted to main admin) have no effect; a main admin always has every section.
- Sections not built yet (careers, pages; settings is a placeholder) can already be granted; the grant takes effect when the section exists.

## Requirements *(mandatory)*

### Functional Requirements

**Roles and permissions**

- **FR-001**: The system MUST support exactly two roles: main admin and content manager.
- **FR-002**: A main admin MUST have access to every admin section, including users, the change record and student registrations, regardless of stored grants.
- **FR-003**: A content manager MUST have access only to the overview, their own Account page, and the sections granted to them from the set {news, messages, careers, settings, pages}.
- **FR-004**: Registrations, users and the change record MUST NOT be grantable and MUST be refused to every content manager.
- **FR-005**: Adding a future grantable section MUST require only defining one new permission key and attaching it to that section; the grant, storage and check mechanisms MUST NOT change.
- **FR-006**: Section-to-key mapping for existing features: News → news; Messages → messages; Signups (004's lead list, including its list, search, delete and CSV export; replaced by Careers in 012) → careers; Settings → settings; page content (future) → pages; notification counts follow the section each count belongs to.

**Enforcement**

- **FR-007**: Every admin page, data request and action MUST check the signed-in user's role and grants on the server on every request, reading current values rather than values captured at login.
- **FR-008**: A page the user may not use MUST redirect to the admin overview and show "You don't have access to that section."
- **FR-009**: A data request or action the user may not use MUST be refused with a "forbidden" outcome (403) that returns no section data. The same outcome applies to grantable sections and to main-admin-only areas (users, change record, registrations). A request with no valid session MUST keep 002's "not signed in" behaviour (401). The raw auth-library routes closed in 010 keep returning "not found" (User Story 6, scenario 7).
- **FR-010**: The sidebar, overview cards and notification bell MUST show only sections the user may use. This is presentation only and MUST NOT be the access control.
- **FR-011**: No user MUST be able to change their own role or grants by any route. Role and grant changes MUST only be accepted from a main admin acting on another account.
- **FR-012**: Disabled and deleted accounts MUST be refused on their next request, whatever sessions they hold.
- **FR-013**: The account actions MUST act only on the caller's own account and ignore any user id or email supplied in the request. "Sign out other devices" and reading the last-changed time stay available to every role; changing a password does not (FR-015).

**The main admin controls every password**

- **FR-014**: There MUST be no forced password change at first login, no temporary-password state and no expiry. The password the main admin sets is the user's password until a main admin changes it.
- **FR-015**: A content manager MUST NOT be able to change any password, their own included. The Account page MUST show them no change-password form, and the server MUST refuse the action for them, including when a user id or email is supplied.
- **FR-016**: A main admin MAY change their own password on the Account page under the 010 rules (current password required, 12 to 128 characters, lockout after repeated failures). They MUST NOT be able to change another user's password there; that is done from the user panel (FR-024).
- **FR-017**: "Sign out other devices" MUST stay available to every role, ending only the caller's own other sessions.
- **FR-018**: A password set by the main admin MUST meet the same length rules as any other password (12 to 128 characters), enforced on the server.

**User management (main admin only)**

- **FR-019**: The system MUST provide a Users page listing all non-deleted accounts with email, role, grants, status (Active or Disabled) and last login time.
- **FR-020**: The main admin MUST be able to create an account with an email, a role (default content manager) and ticked grants. Email MUST be trimmed and lowercased; an email already used by a non-deleted account MUST be refused.
- **FR-021**: Adding an account or resetting a password MUST take a password from the admin — typed, or generated by one click of "Generate" — of 12 to 128 characters (the same rules as any password). It is the user's password as set (FR-014). The password MUST be visible only while the panel is open (hidden by default, revealable), and MUST never be returned, stored readable, logged or recorded.
- **FR-022**: The main admin MUST be able to change another user's grants and role (promote a content manager to main admin, or demote another main admin to content manager). There may be any number of main admins.
- **FR-023**: The main admin MUST be able to disable another user (ending all that user's sessions at once and blocking login) and re-enable them (restoring login with the same password and grants).
- **FR-024**: The main admin MUST be able to reset another user's password from that user's edit panel: filling the password field (typed or generated) sets the new password and ends all that user's sessions. An empty field changes nothing.
- **FR-025**: The main admin MUST be able to delete another user, after a confirmation step, as a soft delete that ends all their sessions and blocks login. Creating an account with a deleted account's email restores that record as a new account.
- **FR-026**: A main admin MUST NOT be able to disable, delete or demote themselves, or change their own role. These controls MUST NOT be offered on their own row, and direct requests MUST be refused.
- **FR-027**: No action MUST leave zero active main admins. This MUST hold even when two such actions happen at the same time.
- **FR-028**: Login failures for disabled or deleted accounts MUST look identical to 002's generic login failure.
- **FR-029**: Every user-management request MUST be accepted only from the admin panel's own origin, like 010's account actions.

**Record of changes**

- **FR-030**: The system MUST record each of: account created (or restored), role changed, grants changed (added and removed sections), disabled, re-enabled, password set by the main admin, and deleted. Each entry holds the acting user, the target user, what changed, and when.
- **FR-031**: Entries MUST NOT contain any password or session identifier, and MUST NOT be editable or deletable through the admin panel.
- **FR-032**: The main admin MUST be able to view the record newest first, with older entries reachable by paging or scrolling.
- **FR-033**: The security events log (002/010 format) MUST also receive: access refused for missing permission, account disabled, account deleted, and password set by the main admin. No password or session identifier appears.

**Seed and existing accounts**

- **FR-034**: The seed command MUST create the initial account as a main admin and MUST stay run-manually-only. Any account that exists before this feature MUST become a main admin.

**Layout**

- **FR-035**: The Users page, the right-hand panel, the change record and the Account page MUST work without horizontal scrolling or overlapping controls at 375, 768, 1024 and 1440px and follow existing admin UI patterns. On narrow widths the user list MAY switch from a table to stacked cards, and on phones the panel MUST open at full width.

**The right-hand panel**

- **FR-036**: Adding and editing a user MUST happen in a panel that slides in from the right over the Users list, not on a separate page. It holds the email (read-only when editing), the role, the password and the section tickboxes. The section tickboxes MUST appear only when Content manager is chosen.
- **FR-037**: Saving MUST close the panel, and the new or changed user MUST appear in the list immediately, without a manual reload.
- **FR-038**: The panel MUST close on Escape, on a click outside it, on its close button and on Cancel. When anything has been typed or changed, it MUST warn first and let the admin stay; with nothing changed it closes at once.

**One password input everywhere**

- **FR-039**: Every password field in the admin — login, the Account page's current, new and confirm fields (main admin only), and the user panel's password — MUST use one shared password input with a show/hide eye toggle. It MUST be hidden by default, operable by keyboard (a real button reached by Tab, with an accessible name that changes with its state), and MUST return to hidden when its form is submitted or reset and when the panel containing it closes. Pasting and password-manager autofill MUST keep working.

### Key Entities

- **User (admin account)**: email (unique, lowercase), role (main admin or content manager), set of granted section keys, status (active or disabled), deleted marker, last login time, password last changed time.
- **Permission key**: a named admin section that can be granted (news, messages, careers, settings, pages). Registrations and users are not keys; they belong to the main admin role.
- **Session**: an existing signed-in session (002). Ended when the account is disabled, deleted or has its password set by the main admin.
- **Change record entry**: actor, target, change type, details (e.g. sections added/removed, old and new role), timestamp. Append-only.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A main admin can add a content manager, using a generated password, in under 1 minute, and the user is in the list without a reload.
- **SC-002**: A content manager who has been given a password can log in and reach their permitted sections on the first attempt, with no extra step.
- **SC-003**: 100% of admin routes have three passing access tests: no session, wrong role or missing permission, correct permission.
- **SC-004**: 0 paths (page or request) let a content manager reach registrations, users, the change record, or another user's account; proven by tests for each.
- **SC-005**: 0 paths let a user raise their own permissions or role; proven by tests.
- **SC-006**: A permission change, disable or delete takes effect on the affected user's very next request in 100% of tested cases, in every open browser, without re-login.
- **SC-007**: 100% of account and permission changes produce a change-record entry with actor, target, change and time, and 0 entries or log lines contain a password.
- **SC-008**: The end-to-end journey passes: add a content manager, log in with the password the admin set, see only permitted sections, get refused at a forbidden URL, see a permission change without re-login, get disabled and lose access.
- **SC-009**: All pages in this feature, including the right-hand panel (full width on phones), pass layout checks at 375, 768, 1024 and 1440px.
- **SC-010**: 100% of the admin's password fields use the shared show/hide input, hidden by default; a revealed password goes back to hidden on submit and on panel close.

## Assumptions

- Student registrations (013) do not exist yet; when built they are main-admin only.
- **settings** and **pages** can be granted now; Settings is currently a placeholder and page content arrives in 014.
- A main admin's stored grants are irrelevant; they always have everything.
- Passwords set in the panel are handed to the person outside the system (in person or by phone); the admin can reveal the password while the panel is open to read it out. No email is sent (Constitution VI). There is no copy-to-clipboard control: revealing is enough for the stated purpose.
- The change record is kept indefinitely in this phase; it holds no personal data beyond admin emails.
- Disabled and deleted accounts fail login with 002's generic message, so login does not reveal account state.
- The overview itself is available to every signed-in, active, password-set user.
- The existing seeded account(s) become main admin when this feature is deployed.

## Dependencies

- Feature 002: login, sessions, lockout, security log format, generic login failure.
- Feature 010: Account page, password rules and messages, per-account lockout, closed raw auth routes. The carried-over acceptance items in `docs/briefs/011-roles-and-users.md` are part of this feature's acceptance.
- Feature 009: notification bell and counts, which become permission-aware.
- ADR "role-permissions-model" is referenced by the brief but does not yet exist in `history/adr/`. It should be written during planning.

## Out of Scope

- More than two roles, or custom roles.
- Invitations or password resets by email (no email service).
- Two-factor authentication.
- Permissions on individual records (a manager with news access can edit every news post).
- Self-service "forgot password"; recovery stays with the main admin (reset) or the seed command.
- Hard deletion of accounts or change-record entries.
